# CI / Release

## GitHub Actions

`.github/workflows/ios.yml` is the PR/main check. It installs XcodeGen, generates
`PitchAtlas.xcodeproj`, builds the app with `xcodebuild`, then runs unit tests on
an available iPhone simulator with `build-for-testing` followed by
`test-without-building` through `./scripts/build.sh test`. The wrapper shuts down
all simulators before each Xcode launch step, waits for `simctl bootstatus -b`
when the destination is pinned by simulator id, gives the test launch a bounded
timeout, and restarts CoreSimulator once if the run stalls at "waiting for
workers to materialize". Do not replace it with `swift build` / `swift test`;
this app is not a SwiftPM executable package.

`scripts/build.sh test` must fail when tests fail. The wrapper uses `pipefail`
and only pipes through `xcpretty` when `xcpretty` exists. A retry is allowed only
for the known Xcode simulator-launch timeout, not for compile errors or failed
tests.

## Xcode Cloud

`PitchAtlas.xcodeproj` is generated by **XcodeGen** from `project.yml` and is not
hand-edited. Xcode Cloud runs `ci_scripts/ci_post_clone.sh` after clone; that
script installs XcodeGen when needed and runs `xcodegen generate`.

The bundled content (`Resources/Content/*.json`) **is** committed, so CI needs no
web repo and no Node. Refreshing content from the web source is a deliberate,
local pre-release step (`cd tools/generate-content && npm i && npm run generate`),
run and committed before tagging a release. CI does not do this per build.

## Workflows

One Xcode Cloud workflow exists (read from the App Store Connect API on
2026-10-30): **Default**, started by every push to `main`, one action: Archive
(the `PitchAtlas` scheme, iOS) with no distribution audience. It is a release
build check, not a delivery path; no Xcode Cloud workflow uploads to TestFlight
or App Store Connect. Builds are delivered from a local signed archive (see
`docs/review-evidence/2026-10-30-build-13-submitted.md`). A Release workflow
that archives and uploads on a tag was planned and never created.

Every workflow runs `ci_post_clone.sh` automatically (Xcode Cloud convention:
any executable in `ci_scripts/` named `ci_post_clone.sh` runs after clone).

Xcode Cloud resolves Swift packages with automatic resolution off, so
`ci_post_clone.sh` copies the pinned `ci_scripts/Package.resolved` into the
generated project. When a package version changes locally, copy
`PitchAtlas.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`
over it and commit, or Xcode Cloud builds against the old pin. (Run 38 on
2026-10-05 failed for want of this file.)

## Release conventions

- **Build numbers are monotonic.** Builds reach App Store Connect only from a
  local signed archive, which keeps `project.yml`'s `CURRENT_PROJECT_VERSION` as
  written, so set it to the exact next build number before archiving and never
  below the last uploaded build. (An Xcode Cloud archive would number above
  that value, but the Default workflow does not upload.)
- **`action_required` means a compile error**, not a manual approval gate. Read
  the build log's error count and fix the code.
- **Same-day merge-back:** a release branch merges back to `main` the day it
  archives, so `main` never drifts behind a shipped build.

## Local build / test

```bash
xcodegen generate
./scripts/build.sh build
./scripts/build.sh test
```

## Supabase Release Gate

Before a release upload, verify the live Supabase project, the iOS community RPCs,
media upload/readback, blocked-content filtering, and the JWT-protected
`delete-account` function. For build `1.0.1 (10)`, the live project had the iOS
preflight migrations, `delete-account`, and authenticated block RPCs
(`block_user`, `unblock_user`, `my_blocked_users`) applied. Also recheck Supabase
branch/migration health from `ahump20/Pitch-Atlas`; prior release notes recorded
`MIGRATIONS_FAILED`, so do not rely on automatic Supabase branch/deploy behavior
if the live console still reports that state.
